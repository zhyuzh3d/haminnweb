# HaminnWeb 快速开发策略

HaminnWeb 的日常开发以“修改到设备生效”的时间为首要效率指标。每次任务先收窄到一个明确行为，只读取相关源码，完成局部修改后运行能够覆盖该风险的最小技术检查，并立即同步目标文件、刷新 HaminnUI。测试的目的在于发现本次修改可能引入的错误，而不是重复证明整个项目仍然存在。

文案调整通常只需要确认目标文本、HTML 结构和脚本语法；局部样式调整只需要检查相关选择器、兼容分支和必要的 DOM 合同；功能逻辑调整才增加对应流程测试；Host API、发布清单、Shell ZIP 或 APK 元数据发生变化时，才运行相应的跨仓合同与制品校验。完整 `flows.test.cjs`、全站资源闭包、Android 构建、签名校验和设备矩阵属于影响面足够大或用户明确要求时的门禁，不是每次迭代的固定前置步骤。

HaminnUI 实时迭代优先直接更新 `public/shell/` 源文件。最小检查通过后同步到 `haminn.airen.life`，只核对本次涉及的公开资源，然后通过智能体开发服务获取当前页面状态，使用原 WebView 无缓存刷新并恢复 tab、滚动位置和仍然可达的弹窗。只有运行模式变化、WebView 状态损坏或用户明确要求时才重建 WebView。

微小实时修改不自动升 HaminnUI 版本，不生成新的发布 ZIP，也不同步 APK 内置快照。形成稳定发布节点、更新本地 Shell、构建 APK 或用户明确要求正式发布时，再集中完成版本号、manifest、ZIP、摘要、内置快照和发布验证，避免把制品工作重复附加到每一次小改上。

默认不进行浏览器或真机视觉测试，不打开页面截图，不做像素和主观外观判断。刷新完成后由用户直接查看设备效果并继续提出修改；只有用户明确要求视觉核查，或技术问题本身无法通过源码、DOM、合同和运行结果定位时，才进入视觉验证。
